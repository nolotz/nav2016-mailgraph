# Research notes

Fact base collected on 2026-10-12 by research agents that read the linked primary sources.
Confidence: **high** = read in an authoritative source; **medium** = community source or indirect evidence.
Treat medium-confidence items as "verify in your environment". The design decisions derived from this are in `DESIGN.md` section 11.


## Microsoft Graph mail API
- [high] POST /users/{id | userPrincipalName}/sendMail (and POST /me/sendMail) with Content-Type application/json; the JSON body is {"message": <message>, "saveToSentItems": <bool>} where message is required and saveToSentItems is optional with default true ("Specify it only if the parameter is false"). (https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0) NOTE: Docs example literally sends "saveToSentItems": "false" as a string, but the parameter type is Boolean; send a JSON boolean.
- [high] A successful sendMail returns 202 Accepted with an empty body, and the docs state 202 only means the request was accepted, not that processing/delivery completed; delivery is subject to Exchange Online limits and throttling. (https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0) NOTE: Malformed MIME gives 400 with error code ErrorMimeContentInvalidBase64String.
- [high] sendMail requires only Mail.Send (Application) as least-privileged permission; the same is true for POST /users/{id}/messages/{id}/send. (https://learn.microsoft.com/en-us/graph/api/message-send?view=graph-rest-1.0) NOTE: Both pages list Application: Mail.Send, higher privileged: Not available.
- [high] Microsoft Graph write requests have a 4 MB size limit; some endpoints are effectively lower (e.g. POST .../attachments is 3 MB because a ~3.5 MB file exceeds 4 MB once base64-encoded), and requests over the limit fail with HTTP 413 and the message 'Request entity too large' or 'Payload too large'. (https://learn.microsoft.com/en-us/graph/use-the-api) NOTE: This is the authoritative source for the 4 MB figure; the sendMail reference page itself does not restate it. A Microsoft Q&A thread (https://learn.microsoft.com/en-gb/answers/questions/2137745/) reports a 10 MB inline attachment succeeding in practice, so the limit is not always enforced, but design for 4 MB total request body.
- [high] A file attachment inside sendMail (or inside a draft) is a JSON object in the message.attachments array with "@odata.type": "#microsoft.graph.fileAttachment", required properties name and contentBytes (base64-encoded file content), plus optional contentType, contentId and isInline. (https://learn.microsoft.com/en-us/graph/api/resources/fileattachment?view=graph-rest-1.0) NOTE: fileAttachment doc: 'Make sure to encode the file content in base64 before assigning it to contentBytes.' contentLocation is documented as unsupported; do not send it.
- [high] A message JSON uses subject (string), body {contentType: "Text"|"HTML", content}, toRecipients/ccRecipients/bccRecipients/replyTo as arrays of {"emailAddress": {"address": ..., "name": ...}}, importance as one of low/normal/high, internetMessageHeaders as an array of {name, value}, and attachments as an array of attachment objects. (https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0) NOTE: recipient resource = {emailAddress: {address, name}} per https://learn.microsoft.com/en-us/graph/api/resources/emailaddress?view=graph-rest-1.0. Examples send importance as "Low" and body.contentType as "Text"/"HTML"; responses echo lowercase ("low", "html"), so enum matching is case-insensitive on input.
- [high] The maximum total number of recipients across toRecipients, ccRecipients and bccRecipients for a single message from an Exchange Online mailbox is 500 by default (Exchange admins can customize the per-mailbox recipient limit between 1 and 1000). (https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0) NOTE: 500 is stated on the message resource page; the 1-1000 customizable range is on https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits#sending-limits.
- [high] Custom Internet message headers may only be added when creating a message (sendMail or draft POST), must be named starting with "x-", cannot be modified after sending, and are read-only/require $select on GET; the POST response does not return them by default. (https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0) NOTE: No documented limit on count or size of custom headers was found.
- [high] The from property must correspond to the actual mailbox used; set from to send as another mailbox only when that mailbox has granted Send As rights, and leave sender unset because Graph sets it (sender differs from from only in Send-on-Behalf/delegate scenarios). (https://learn.microsoft.com/en-us/graph/outlook-send-mail-from-other-user) NOTE: Also https://learn.microsoft.com/en-us/graph/outlook-create-send-messages#set-the-from-and-sender-properties and the message resource property table.
- [high] With application tokens, an app that has admin-consented Mail.Send can send as any user by posting to that user's own mailbox (POST /users/{thatUser}/sendMail) without setting from; this is the documented way to send 'as' a mailbox with app permissions rather than changing from. (https://learn.microsoft.com/en-us/graph/outlook-send-mail-from-other-user) NOTE: Quote: 'Applications that use application tokens instead of user tokens and have the Mail.Send permission consented by an administrator can send mail as any user in the organization by sending the mail normally through the user's mailbox.'
- [high] If from is set to a mailbox for which the sending mailbox lacks Send As / Send on Behalf rights, Graph returns HTTP 403 with error.code "ErrorSendAsDenied" and message 'The user account which was used to submit this request does not have the right to send mail on behalf of the specified sending account. Cannot submit message.' (https://learn.microsoft.com/en-us/graph/outlook-send-mail-from-other-user) NOTE: The documented example is a delegated (/me) call; the same Exchange Send As check applies to the URL mailbox under application permissions, but that exact combination is not shown in docs (medium confidence for app-only).
- [high] When sending via /users/{user-id} where user-id is the from user, the message is saved by default in the from user's Sent Items; saveToSentItems=false suppresses saving except when an admin has configured 'always save a copy of messages sent from a delegate'. (https://learn.microsoft.com/en-us/graph/outlook-send-mail-from-other-user) NOTE: If the from address has no mailbox (e.g. a distribution list) there is no Sent Items copy for it.
- [high] POST /users/{id|userPrincipalName}/messages with a message JSON creates a draft in Drafts, returns 201 Created with the full message object (including id, isDraft:true), requires Mail.ReadWrite (Application), and may include attachments inline in the same request. (https://learn.microsoft.com/en-us/graph/api/user-post-messages?view=graph-rest-1.0) NOTE: Note on that page: S/MIME (MIME-format) payloads are limited to 4 MB and exceeding it returns HTTP 413 Request Entity Too Large.
- [high] POST /users/{id|userPrincipalName}/messages/{id}/attachments adds a fileAttachment (JSON body: @odata.type #microsoft.graph.fileAttachment, name, contentBytes, optional contentType/isInline/contentId), is limited to attachments under 3 MB, returns 201 Created with the attachment object, and requires Mail.ReadWrite (Application). (https://learn.microsoft.com/en-us/graph/api/message-post-attachments?view=graph-rest-1.0) NOTE: 'This operation limits the size of the attachment you can add to under 3 MB.'
- [high] POST /users/{id|userPrincipalName}/messages/{id}/attachments/createUploadSession with body {"AttachmentItem": {"attachmentType": "file", "name": "...", "size": <bytes>, optional "contentType", "isInline", "contentId"}} returns 201 Created with an uploadSession {uploadUrl, expirationDateTime, nextExpectedRanges:["0-"]}; it is for files between 3 MB and 150 MB, and for messages requires Mail.ReadWrite. (https://learn.microsoft.com/en-us/graph/api/attachment-createuploadsession?view=graph-rest-1.0) NOTE: attachmentItem: attachmentType (file|item|reference, required), name (required), size Int64 (required), contentType/isInline/contentId optional (https://learn.microsoft.com/en-us/graph/api/resources/attachmentitem?view=graph-rest-1.0). Permission table lists Calendars.ReadWrite as least privileged (for events) and Mail.ReadWrite as the one needed for messages; the large-attachments guide says 'Make sure to request Mail.ReadWrite permission to create the uploadSession for a message'. Files under 3 MB fail with ErrorAttachmentSizeShouldNotBeLessThanMinimumSize.
- [high] Each chunk is a PUT to uploadUrl with headers Content-Type: application/octet-stream, Content-Length: <bytes in this PUT>, Content-Range: bytes {start}-{end}/{total} (0-based, inclusive end), raw binary body, uploaded strictly in order; Microsoft recommends keeping each range under 4 MB ('up to 4 MB each time'). (https://learn.microsoft.com/en-us/graph/outlook-large-attachments) NOTE: The Outlook docs specify no 320 KiB alignment; that rule (multiples of 327,680 bytes, max 60 MiB per PUT) belongs to the OneDrive driveItem upload session (https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0) and is not stated for Outlook attachments.
- [high] Do NOT send an Authorization header on the PUT (or DELETE) to uploadUrl: the URL is pre-authenticated (contains an authtoken query parameter) for the https://outlook.office.com domain and must not be customized; the token expires at expirationDateTime. (https://learn.microsoft.com/en-us/graph/outlook-large-attachments) NOTE: Quote: 'Do not specify an Authorization request header. The PUT query uses a pre-authenticated URL from the uploadUrl property'. Note the uploadUrl host is outlook.office.com, not graph.microsoft.com, so a Graph-scoped HttpClient with a default Authorization header must not be reused for these PUTs.
- [high] Intermediate PUTs return 200 OK with a JSON body containing ExpirationDateTime and nextExpectedRanges (for Outlook always a single value like ["2097152"], the next byte offset); the final PUT returns 201 Created with Content-Length: 0 and a Location header whose URL ends in /Attachments('{attachmentId}'). (https://learn.microsoft.com/en-us/graph/outlook-large-attachments) NOTE: uploadSession resource: 'When uploading files as Outlook attachments ... this property always indicates a single value "{start}"' (https://learn.microsoft.com/en-us/graph/api/resources/uploadsession?view=graph-rest-1.0). Note the intermediate response uses PascalCase 'ExpirationDateTime' in the example. Cancel with DELETE uploadUrl -> 204.
- [high] POST /users/{id|userPrincipalName}/messages/{id}/send with no body and header Content-Length: 0 (documented as required) sends the draft, saves it to Sent Items and returns 202 Accepted with empty body; requires Mail.Send (Application). (https://learn.microsoft.com/en-us/graph/api/message-send?view=graph-rest-1.0) NOTE: With HttpClient, send an empty content (e.g. new ByteArrayContent(Array.Empty<byte>())) so Content-Length: 0 is emitted.
- [high] The draft + attachment + send flow with application permissions needs BOTH Mail.ReadWrite (create draft, add attachment, createUploadSession, delete draft) AND Mail.Send (send); Mail.ReadWrite explicitly 'Does not include permission to send mail', and Mail.Send alone suffices for sendMail including saving to Sent Items. (https://learn.microsoft.com/en-us/graph/permissions-reference) NOTE: Mail.Send application permission id b633e1c5-b582-4048-a93e-9f11b44c7e96 ('Send mail as any user', admin consent required); Mail.ReadWrite application id e2a3a72e-5f79-4c64-b1b1-878b674786c9 ('Read and write mail in all mailboxes', admin consent required). Quote: 'With the Mail.Send permission, an app can send mail and save a copy to the user's Sent Items folder, even if the app isn't granted the Mail.ReadWrite or Mail.ReadWrite.Shared permission.'
- [high] Application mail permissions apply to all mailboxes in the tenant unless scoped; the legacy New-ApplicationAccessPolicy (-AccessRight RestrictAccess|DenyAccess -AppId -PolicyScopeGroupId) is being replaced by RBAC for Applications (New-ServicePrincipal + New-ManagementRoleAssignment -App <sp> -Role "Application Mail.Send" -CustomResourceScope <scope>), and permission changes are cached for 30 minutes to 2 hours. (https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac) NOTE: https://learn.microsoft.com/en-us/graph/auth-limit-mailbox-access now redirects to the RBAC page. New-ApplicationAccessPolicy page: 'Don't create new App Access Policies as these policies will eventually require migration' (https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/new-applicationaccesspolicy). Test with Test-ServicePrincipalAuthorization -Identity <app> -Resource <mailbox>. A denied mailbox yields a 403 from Graph.
- [high] Graph errors are a JSON object {"error": {"code": string, "message": string, "innerError": {...}, "details": [...]}}; code is the only value to depend on in code, message is for developers and not localized, and innerError commonly carries "request-id", "date", "client-request-id" and sometimes a nested "code". (https://learn.microsoft.com/en-us/graph/errors) NOTE: Observed innerError variants in docs: {code, request-id, date} (errors page), {request-id, date} (ErrorSendAsDenied example), {date, request-id, client-request-id} (known-issues example), {code, date, message, request-id, status} (throttling example). Parse innerError leniently and log request-id/date.
- [high] When throttled Graph returns 429 Too Many Requests with error.code "TooManyRequests" and a Retry-After response header in seconds (example 'Retry-After: 10'); the guidance is to wait that many seconds, retry, and keep honoring Retry-After on repeated 429s, falling back to exponential backoff if the header is absent. (https://learn.microsoft.com/en-us/graph/throttling) NOTE: Immediate retries still count against limits. Batched requests are evaluated individually (429 inside a 200 batch).
- [high] 503 Service Unavailable means the service is busy; back off like a 429 (Retry-After may be present) and always issue retries over a new HTTP connection; 509 Bandwidth Limit Exceeded is another throttling code and 413 means the request exceeded the size limit. (https://learn.microsoft.com/en-us/graph/best-practices-concept) NOTE: Status table at https://learn.microsoft.com/en-us/graph/errors.
- [high] Outlook (mail API) limits apply per app ID + mailbox combination: 10,000 API requests per 10-minute period, 4 concurrent requests, and 150 MB of upload (PATCH/POST/PUT) per 5-minute period; plus a global limit of 130,000 requests per 10 seconds per app across all tenants. (https://learn.microsoft.com/en-us/graph/throttling-limits) NOTE: Exceeding one mailbox's limit does not affect other mailboxes. The 150 MB/5 min upload cap matters for many large-attachment sends from a single sending mailbox. These limits apply to public and national clouds.
- [high] Exchange Online enforces per-mailbox sending limits of 10,000 recipients per 24-hour period (recipient rate limit), 30 messages per minute (message rate limit; excess is throttled and carried over to following minutes), and 500 recipients per message by default (customizable 1-1000). (https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits) NOTE: Page explicitly says these limits 'prevent users and applications from sending large volumes of email' and that 'Exchange Online isn't suited to accommodate bulk-mailing scenarios'; it recommends Azure Communication Services email for high-volume external mail. After hitting the recipient rate limit the mailbox cannot send until the rolling 24h count drops.
- [high] Beyond per-mailbox limits there is a Tenant External Recipient Rate Limit (TERRL) per 24-hour sliding window that depends on license count (trial tenants capped at 5,000 external recipients/day), and outbound mail from default *.onmicrosoft.com domains is limited to 100 external recipients per organization per 24 hours (NDR 550 5.7.236 when exceeded). (https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits) NOTE: Relevant for an ERP sending invoices to many external customers; use a verified custom domain.
- [high] The default maximum message size for Microsoft 365 mailboxes is 35 MB for sending (36 MB receiving) including attachments; admins can set 1-150 MB, and messages routed outside Microsoft datacenters are subject to a 33% encoding increase (effective max 112 MB). (https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits) NOTE: createUploadSession page repeats: 'By default, this message size limit is 35 MB.' A 150 MB attachment upload will still bounce (NDR) unless the tenant's limit is raised.
- [high] After sendMail returns 202 the message has only been saved as a draft and handed to transport; invalid recipients, policy rejections and size violations surface later as non-delivery reports placed in the sender's Inbox, so the API response cannot be used as proof of delivery. (https://learn.microsoft.com/en-us/graph/outlook-things-to-know-about-send-mail) NOTE: Steps 2-7 happen after the response.
- [high] With delegated permissions, createUploadSession returns 403 Forbidden when the message/event is in a shared or delegated mailbox (it succeeds only in the signed-in user's own mailbox); the known-issues page does not list this restriction for application permissions. (https://learn.microsoft.com/en-us/graph/known-issues) NOTE: The createUploadSession and large-attachments pages link this as known issue 13644. An app-only ERP addressing /users/{sharedMailbox} is not the delegated case.
- [high] When addressing /users/{userPrincipalName}, percent-encode '#' as %23 (e.g. /users/AdeleVance_adatum.com%23EXT%23@contoso.com for B2B guests), and for a UPN beginning with '$' use the parenthesized form /users('$x@y.com') because /users/$x@y.com fails with 400 Bad Request. (https://learn.microsoft.com/en-us/graph/api/user-get?view=graph-rest-1.0) NOTE: '@' may be left unencoded in the path (all official examples do so). A user's object id (GUID) avoids encoding issues entirely.
- [high] Graph service roots are https://graph.microsoft.com (global, also used for GCC), https://graph.microsoft.us (US Government L4 / GCC High), https://dod-graph.microsoft.us (US Government L5 / DoD) and https://microsoftgraph.chinacloudapi.cn (China operated by 21Vianet); token endpoints are https://login.microsoftonline.com, https://login.microsoftonline.us (both US Gov) and https://login.chinacloudapi.cn. (https://learn.microsoft.com/en-us/graph/deployments) NOTE: Tokens for one cloud are not interchangeable with another.
- [high] sendMail, create draft, add attachment (<3 MB) and send draft are available in Global, US Gov L4, US Gov L5 and China, but attachment createUploadSession is marked NOT available in US Government L4 and L5 (available in Global and China). (https://learn.microsoft.com/en-us/graph/api/attachment-createuploadsession?view=graph-rest-1.0) NOTE: Availability tables on each API page; for GCC High/DoD the library cannot use the large-attachment flow and must fall back to the 4 MB inline path.
- [high] Microsoft recommends generating a unique GUID per request, sending it in the client-request-id request header and logging it, together with the full request/response (URL, headers, JSON) so support can trace the call; Graph always returns a request-id response header and echoes client-request-id. (https://learn.microsoft.com/en-us/graph/best-practices-concept) NOTE: Graph activity logs (MicrosoftGraphActivityLogs) record ClientRequestId (defaults to the operation id if none was sent), RequestId, UserAgent, AppId, ServicePrincipalId, RequestMethod, RequestUri and ResponseStatusCode (https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/microsoftgraphactivitylogs).
- [high] Microsoft Graph documents no required User-Agent format; the official .NET SDK does not set User-Agent but adds an SdkVersion header formatted 'graph-dotnet-core/{major}.{minor}.{build}' (optionally prefixed by 'graph-dotnet/{version},') plus a client-request-id GUID when absent. (https://raw.githubusercontent.com/microsoftgraph/msgraph-sdk-dotnet-core/main/src/Microsoft.Graph.Core/CoreConstants.cs) NOTE: Header names from CoreConstants: SdkVersionHeaderName = "SdkVersion", ClientRequestId = "client-request-id", format "graph-dotnet-core/{0}.{1}.{2}"; GraphTelemetryHandler appends hostOS/hostArch/runtimeEnvironment. Since Microsoft logs UserAgent per request, send a descriptive RFC 7231 product token (e.g. 'nav2016-mailgraph/1.0.0').
- [high] Requests take the form {HTTP method} https://graph.microsoft.com/{version}/{resource}?{query-parameters}; use v1.0 for production, and headers are case-insensitive. (https://learn.microsoft.com/en-us/graph/use-the-api) NOTE: Retry-After is returned on throttling and Location on long-running operations.
- [high] For an inline image set isInline: true and contentId (e.g. "my_inline_picture") on the attachment (both for fileAttachment and AttachmentItem in createUploadSession) and reference it from the HTML body as <img src="cid:my_inline_picture">; hasAttachments stays false when a message has only inline attachments. (https://learn.microsoft.com/en-us/graph/api/attachment-createuploadsession?view=graph-rest-1.0) NOTE: hasAttachments note from the message resource page.
- [medium] The whole file must be uploaded before expirationDateTime; for Outlook attachments the docs say the expiration returned on intermediate PUTs 'remains the same as returned by the initial uploadSession' (the generic uploadSession page says fragments extend it, but the Outlook guide does not promise that). (https://learn.microsoft.com/en-us/graph/outlook-large-attachments) NOTE: Documented example expirations are roughly 24 hours after creation; treat expirationDateTime as a hard deadline and recreate the session (new draft attachment) if it passes.
- [high] Graph sends at most four unordered requests from a JSON batch to the Outlook service in parallel (matching the 4-concurrent-request mailbox limit); dependsOn makes them sequential. (https://learn.microsoft.com/en-us/graph/throttling-limits) NOTE: Useful if the library ever batches many sendMail calls; each batched request is still throttled individually.
**Open questions:** 
- Exact behavior of sendMail payloads between 4 MB and the mailbox limit: use-the-api documents a hard 4 MB / HTTP 413 write limit, but a Microsoft Q&A thread (Dec 2024) reports a 10 MB inline attachment succeeding and Microsoft staff could not explain the discrepancy; no official statement reconciles them.
- Whether ErrorSendAsDenied is the exact error code returned under application permissions when message.from differs from the URL mailbox and Send As is not granted: the documented 403/ErrorSendAsDenied example uses a delegated /me call; the app-only case is implied but not shown.
- The uploadUrl host for createUploadSession in the China (21Vianet) cloud: docs show https://outlook.office.com/api/... only for the global cloud; the China host was not found in documentation.
- Whether an upload session's expirationDateTime is extended by each PUT for Outlook attachments: the generic uploadSession page says each fragment extends it, while the Outlook guide says the value stays the same as the initial session.
- Any documented maximum count or byte size for custom internetMessageHeaders; the docs only state the 'x-' prefix and create-time-only rules.
- Whether the Outlook upload PUT endpoint (outlook.office.com) returns 429 with Retry-After in the same way as graph.microsoft.com; the throttling docs cover Graph endpoints only.
- Whether percent-encoding '@' as %40 in the /users/{upn} path segment is accepted; all official examples leave '@' literal and only document encoding '#' as %23.
**Recommendations:** 
- Default to POST /users/{id}/sendMail with inline fileAttachments when the base64-encoded JSON body stays under 4 MB (budget ~3 MB of raw attachment bytes, since base64 adds ~33% plus body/headers), and switch to the draft flow when it does not.
- Draft flow per message: POST /users/{id}/messages (201, capture id) -> for each file <3 MB POST .../messages/{id}/attachments, for each file 3-150 MB POST .../attachments/createUploadSession then PUT chunks (e.g. 3-4 MB, 'bytes s-e/total', application/octet-stream, no Authorization header, separate HttpClient without default auth) until 201 Created -> POST .../messages/{id}/send with Content-Length: 0 (202); on any failure DELETE the draft to avoid orphaned drafts.
- Request both Mail.Send and Mail.ReadWrite application permissions (admin consent) if the library supports the draft/large-attachment path; if only sendMail is used, Mail.Send alone is sufficient and is the least-privilege choice.
- Address the mailbox by object id (GUID) when available; otherwise percent-encode the UPN path segment (at minimum '#' -> %23) and handle UPNs starting with '$' via /users('...').
- Send 'as' a mailbox by targeting that mailbox in the URL (/users/{mailbox}/sendMail) rather than setting message.from; only set from when Exchange Send As rights exist, and surface 403 ErrorSendAsDenied as a configuration error, not a retryable one.
- Treat 429 (and 503/509) as retryable: honor Retry-After (seconds) when present, otherwise exponential backoff with jitter; retry 503 on a fresh connection; never retry 4xx such as 400/403/404/413.
- Rate-limit the sender in the library to stay under Exchange's 30 messages/minute and 10,000 recipients/day per sending mailbox, and under Graph's 4 concurrent requests and 150 MB upload per 5 minutes per mailbox; consider multiple sending mailboxes or Azure Communication Services email for high-volume invoice runs.
- Generate a new GUID per request in client-request-id, set a descriptive User-Agent product token, and log client-request-id, the response request-id and Date headers, and the error.code/innerError block for every non-2xx response.
- Parse errors as {error:{code,message,innerError:{...}}} with all innerError fields optional, branch only on error.code (e.g. ErrorSendAsDenied, TooManyRequests, ErrorAttachmentSizeShouldNotBeLessThanMinimumSize, ErrorMimeContentInvalidBase64String), and never on message text.
- Make the Graph base URL configurable with presets for Global (https://graph.microsoft.com), US Gov L4 (https://graph.microsoft.us), US Gov L5 (https://dod-graph.microsoft.us) and China (https://microsoftgraph.chinacloudapi.cn) plus matching login authorities, and disable the upload-session path for the two US Government clouds where createUploadSession is not available.
- Document for operators that the per-mailbox message size limit (default 35 MB) can cause NDRs even when a 150 MB upload succeeds, and that admins can scope the app to specific mailboxes with RBAC for Applications (Application Mail.Send / Application Mail.ReadWrite roles) rather than tenant-wide access.

## Exchange Online RBAC for Applications and Entra app registration
- [high] Microsoft Learn (article dated 2025-11-25, updated 2026-08-21) states RBAC for Applications 'extends the current RBAC model in Exchange Online and it replaces Application Access Policies. These permission grants are independent of the unscoped grants in Microsoft Entra ID.' (https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac) NOTE: The old Graph doc https://learn.microsoft.com/en-us/graph/auth-limit-mailbox-access now redirects to this article (canonical URL is the RBAC page).
- [high] New-ServicePrincipal -AppId <Client Application ID in AAD> -ObjectId <Service principal object ID in AAD> -DisplayName <name>; the doc warns 'Don't use the IDs from the App Registrations page' - ObjectId is the Enterprise application (service principal) Object ID, i.e. Get-MgServicePrincipal .Id, and AppId is Get-MgServicePrincipal .AppId. (https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/new-serviceprincipal) NOTE: The older -ServiceId parameter 'is being deprecated. Use the ObjectId parameter instead.' Cmdlet is Exchange Online only.
- [high] New-ManagementScope [-Name] <String> -RecipientRestrictionFilter <String> creates the resource scope; the filter uses OPATH syntax "Property -ComparisonOperator 'Value'", Name max 64 chars, and the RBAC article example is New-ManagementScope -Name "Canadian users" -RecipientRestrictionFilter "CustomAttribute1 -eq '012332'". (https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/new-managementscope) NOTE: 'Exclusive management scopes don't restrict app access' (RBAC article Limitations).
- [high] Filterable recipient properties include Alias, EmailAddresses, DisplayName, Name, UserPrincipalName, ExternalDirectoryObjectId, CustomAttribute1-15 and MemberOfGroup (distinguished name only; 'works only with groups that Exchange recognizes, so Microsoft Entra security groups don't work'), and the doc says 'Don't use the PrimarySmtpAddress property; use the EmailAddresses property instead.' (https://learn.microsoft.com/en-us/powershell/exchange/recipientfilter-properties) NOTE: Office 365 IT Pros primer (2026-02-17) scoped to one mailbox with -RecipientRestrictionFilter "displayName -eq 'Azure Management Account'" and verified it with Get-Recipient -RecipientPreviewFilter (https://office365itpros.com/2026/02/17/mail-send-rbac-for-applications/).
- [high] To scope by group the RBAC article uses a MemberOfGroup DN filter (e.g. "MemberOfGroup -eq 'CN=...,OU=...onmicrosoft.com,OU=Microsoft Exchange Hosted Organizations,DC=...'"), with limitations 'Nested group members are considered out of scope' and 'Microsoft 365 Groups, Mail-Enabled Security Groups, and Distribution Lists are supported'; alternatively New-ManagementRoleAssignment has -RecipientGroupScope <GroupIdParameter> (direct members only) and -RecipientAdministrativeUnitScope. **Recommendations:** 
- Use RBAC for Applications, not Application Access Policies (Microsoft: 'Don't create new App Access Policies'). Register the app with NO Microsoft Graph Mail.Send application permission and no admin consent in Entra; grant Mail.Send only in Exchange with a scope. If Mail.Send is already consented in Entra, remove it, otherwise the union with the scoped grant leaves the app unrestricted.
- Script order (Graph PowerShell SDK 2.41.x + ExchangeOnlineManagement 3.10.1 on PowerShell 7.6 / macOS 14+): Connect-MgGraph -Scopes 'Application.ReadWrite.All'; $app = New-MgApplication -DisplayName 'NAV2016 MailGraph' -SignInAudience AzureADMyOrg -KeyCredentials @(@{Type='AsymmetricX509Cert';Usage='Verify';Key=$cert.RawData}); $sp = New-MgServicePrincipal -AppId $app.AppId; Connect-ExchangeOnline -UserPrincipalName <Exchange Administrator>; New-ServicePrincipal -AppId $app.AppId -ObjectId $sp.Id -DisplayName $app.DisplayName; New-ManagementScope -Name 'MailGraph sender' -RecipientRestrictionFilter "ExternalDirectoryObjectId -eq '<mailbox Entra object id>'" (or Alias/EmailAddresses; verify with Get-Recipient -RecipientPreviewFilter that exactly one recipient matches); New-ManagementRoleAssignment -App $sp.Id -Role 'Application Mail.Send' -CustomResourceScope 'MailGraph sender'; Test-ServicePrincipalAuthorization -Identity $sp.Id -Resource <sender mailbox> (expect InScope True) and against another mailbox (expect False).
- For a group of mailboxes use a mail-enabled security group / DL / M365 Group with -RecipientRestrictionFilter "MemberOfGroup -eq '<group DistinguishedName from Get-Group>'" or New-ManagementRoleAssignment -RecipientGroupScope <group>; remember nested members are out of scope and Entra-only security groups do not work.
- Prefer a certificate (or federated credential / managed identity) over a client secret; if a secret is unavoidable, create it with Add-MgApplicationPassword with endDateTime <= 12 months, store it only in a secrets store, and consider a tenant app management policy (passwordLifetime / passwordAddition) to enforce this.
- Use a shared mailbox as the sender: it needs no license under 50 GB, keep its sign-in blocked, send with POST /users/<shared-smtp>/sendMail (or Send-MgUserMail -UserId) using client-credentials tokens for https://graph.microsoft.com/.default; expect a 403 for any mailbox outside the scope.
- Allow for the Exchange permission cache (30 minutes to 2 hours) after creating or changing the role assignment; Test-ServicePrincipalAuthorization bypasses the cache so a real sendMail test may lag behind it. Add a retry/wait in the setup script and do not debug 403s inside that window.
- Only add 'AppRoleAssignment.ReadWrite.All' to the admin Connect-MgGraph scopes (and New-MgServicePrincipalAppRoleAssignment with ResourceId = Graph SP id, AppRoleId = b633e1c5-b582-4048-a93e-9f11b44c7e96) if you deliberately want tenant-wide Mail.Send; for the scoped design it is unnecessary.
- 'Assignment required' on the enterprise app does not scope mailbox access; it can be set to true as hardening so no other client can obtain role-less tokens for your app, but mailbox restriction must come from Exchange RBAC.
- On macOS use Connect-ExchangeOnline interactively (browser SSO) or, for unattended runs, -Certificate/-CertificateFilePath with -AppID -Organization, since -CertificateThumbprint is Windows-only; Connect-IPPSSession is unavailable on macOS but is not needed here.
- Keep the az cli variant for CI: az ad app create --display-name X --sign-in-audience AzureADMyOrg; az ad sp create --id $appId; az ad app credential reset --id $appId --cert @cert.pem --append; skip 'az ad app permission add/admin-consent' for Mail.Send when using Exchange RBAC.

## Open points and contradictions
**Contradictions noted:** 
- Target framework: the nav2016 recommendations say 'Build the Graph DLL as AnyCPU targeting .NET Framework 4.7.2', while the msal and build-toolchain recommendations (and the project brief) specify net462;netstandard2.0.
- TLS: the msal recommendation says 'Do not set ServicePointManager.SecurityProtocol in library code' (and 'if you must, use SecurityProtocolType.SystemDefault', a name that does not exist when compiling for 4.6.2), whereas the build-toolchain recommendation says to execute 'ServicePointManager.SecurityProtocol |= SecurityProtocolType.Tls12' as a defensive fallback at initialization.
- Entra permission grants: graph-api recommends 'Request both Mail.Send and Mail.ReadWrite application permissions (admin consent)' and msal assumes granted app roles in the .default token, while exchange-rbac's 'CRUCIAL' facts and recommendations say to register the app with NO Graph Mail.Send permission and no admin consent, because a tenant-wide grant plus a scoped RBAC grant yields no effective scoping. exchange-rbac also assigns only 'Application Mail.Send' in its script and never addresses the Mail.ReadWrite role the draft/large-attachment flow requires.
- JSON serializer: nav2016 recommends 'MSAL + System.Text.Json or a hand-rolled HttpClient/Graph REST call', while build-toolchain designs the DTO layer around DataContractJsonSerializer and justifies it with 'STJ 6.x on net462 pulls additional dependencies' even though the msal section shows System.Text.Json 6.0.10 is already a mandatory part of the MSAL closure.
- AssemblyResolve: the build-toolchain fact states 'AssemblyResolve handlers do not help because they fire only on failed loads', yet the same section and the msal section describe the strong-name version mismatch precisely as a failed load (FileLoadException 'manifest definition does not match'), which is the case AssemblyResolve is designed to handle.
- Binding redirects scope: the msal recommendation says the class library 'cannot carry binding redirects' and lists redirects for all 12 dependency assemblies, while build-toolchain shows GenerateBindingRedirectsOutputType producing a .dll.config and that only System.Memory (->4.0.1.2) and System.Runtime.CompilerServices.Unsafe (->6.0.0.0) actually needed redirects.
- Strong naming: nav2016 says signing is optional ('PublicKeyToken=null is supported'), while build-toolchain recommends SignAssembly=true with a committed .snk; the DotNet subtype string in Codeunit 400 (PublicKeyToken=null vs a token) depends on which is chosen.
- CopyLocalLockFileAssemblies default: the Learn msbuild-props page says false for class libraries, but the SDK source and the measured net462 build say true (and it flips to false for netstandard2.0/net8.0 TFMs).
- '@odata.type' key: the .NET 9 DataContractJsonSerializer emitted the key verbatim, but the .NET Framework WCF docs say the serializer XML-encodes key names that are not valid XML names (medium confidence in build-toolchain).
- Exchange -App parameter: the New-ManagementRoleAssignment reference says it expects the service principal ObjectId GUID from Get-ServicePrincipal, the RBAC article says ObjectID, AppID or DisplayName are accepted, and the Office 365 IT Pros primer used the AppId.
- RBAC propagation delay: Microsoft states 30 minutes to 2 hours of cache, Practical 365 observed up to 30 minutes, Office 365 IT Pros (2026) reported the assignment effective immediately.
- Certificate lifetime: the Graph 'add a certificate' how-to says keyCredential endDateTime can be at most one year after startDateTime, while az ad app credential reset accepts --years N (default 1) with no stated cap.
- Upload session expiry: the generic uploadSession resource page says each uploaded fragment extends expirationDateTime, while the Outlook large-attachments guide says the value returned on intermediate PUTs 'remains the same as returned by the initial uploadSession'.
- AADSTS code for '/common not supported with client credentials': the MSAL error-handling page labels it AADSTS90010, the Entra reference table lists it as AADSTS9001023 and defines AADSTS90010 differently.
- Graph write size limit: use-the-api documents a hard 4 MB limit with HTTP 413, while a Microsoft Q&A thread reports a 10 MB inline attachment succeeding and Microsoft staff could not reconcile the two.
- Shared mailbox as sender: the exchange-rbac fact rates 'unlicensed shared mailbox can be the app-only sender' as medium confidence with no first-party source, but the recommendations state 'Use a shared mailbox as the sender' as settled.
- Add-ins folder probing: Microsoft says assemblies may be put in 'a subfolder' of Add-ins, ForNAV says NAV searches 'the entire folder structure'; whether arbitrary depth and dependency DLLs are resolved is unverified while the recommendation relies on a version-named subfolder holding all 13 dependencies.
**Gaps that still need a test on a real NAV server / tenant:**
- What TargetFrameworkAttribute / <supportedRuntime sku> does NAV 2016's Microsoft.Dynamics.Nav.Server.exe (and finsql.exe) declare, and has Microsoft published TLS 1.2 guidance for NAV 2016 (SchUseStrongCrypto / SystemDefaultTlsVersions registry values or a CU-level fix)? The AppContext TLS defaults are decided by the HOST process's target, not by the add-in's net462 target.

Does it honor an add-in's .dll.config, does Microsoft.Dynamics.Nav.Server.exe.config already contain an <assemblyBinding> section, and is AppDomain.AssemblyResolve raised on a strong-name version mismatch (FileLoadException) so the library can self-redirect System.Memory 4.0.1.1->4.0.1.2 and System.Runtime.CompilerServices.Unsafe ->6.0.0.0 without editing NAV's exe.config?
