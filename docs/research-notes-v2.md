# Research notes v2

Collected 2026-10-12 for the v2 features (reading/polling, large attachments, object storage). Same conventions as `research-notes.md`.

## Microsoft Graph: reading and polling mail

- [high] Messages in a folder are listed with GET /users/{id | userPrincipalName}/mailFolders/{id}/messages; the default page size is 10, and $top accepts values from 1 to 1000. (https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0)
- [high] Microsoft recommends $select to cut response time and warns that large $top pages with full payloads can cause an HTTP 504 gateway timeout, so use a small $select list and a moderate $top (for example 25 to 50) for polling. (https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0) NOTE: The 25-50 page size is our design suggestion. The doc only gives the 504 warning.
- [high] For the next page, request the entire @odata.nextLink URL unchanged; the docs say not to parse or change its $skip value, which can be larger than the page size even on the first response. (https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0)
- [high] When $filter and $orderby are combined on messages, every $orderby property must also appear in $filter, in the same order, and before any other filter properties; otherwise Graph returns error code InefficientFilter ('The restriction or sort order is too complex for this operation.'). (https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0) NOTE: So '$filter=receivedDateTime ge 2026-10-12T08:00:00Z and isRead eq false&$orderby=receivedDateTime asc' satisfies the rules, while '$filter=isRead eq false&$orderby=receivedDateTime' breaks them.
- [high] List and get message calls return body and uniqueBody as HTML by default; sending 'Prefer: outlook.body-content-type="text"' returns text, and the response then carries 'Preference-Applied: outlook.body-content-type="text"'. (https://learn.microsoft.com/en-us/graph/outlook-create-send-messages)
- [high] By default Outlook strips potentially unsafe HTML (for example JavaScript) from body; the request header 'Prefer: outlook.allow-unsafe-html' returns the original HTML. (https://learn.microsoft.com/en-us/graph/outlook-create-send-messages)
- [high] For listing messages with application permissions, Mail.ReadBasic.All is least privileged and Mail.Read and Mail.ReadWrite are higher; delta has the same set. (https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0)
- [high] Mail.ReadBasic excludes body, previewBody, attachments and extended properties (per the Exchange 'Application Mail.ReadBasic' role description), so a NAV inbox reader that needs bodies or attachments needs at least Mail.Read. (https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac)
- [high] Listing and getting message attachments (including /$value) requires Mail.Read as the application permission. (https://learn.microsoft.com/en-us/graph/api/attachment-get?view=graph-rest-1.0)
- [high] PATCH (for example isRead), POST .../move, DELETE of a message, and POST /users/{id}/mailFolders (create folder) each require Mail.ReadWrite as the application permission; no lower permission is listed. (https://learn.microsoft.com/en-us/graph/api/message-update?view=graph-rest-1.0) NOTE: The same Mail.ReadWrite requirement is confirmed on message-move, message-delete and user-post-mailfolders.
- [high] Exchange Online RBAC for Applications provides the app roles 'Application Mail.Read', 'Application Mail.ReadBasic', 'Application Mail.ReadWrite' and 'Application Mail.Send' (plus 'Application Mail Full Access' = Mail.ReadWrite + Mail.Send); they are assigned with New-ManagementRoleAssignment -App <id> -Role "Application Mail.ReadWrite" -CustomResourceScope <scope> (or -RecipientAdministrativeUnitScope), after New-ServicePrincipal -AppId -ObjectId -DisplayName. (https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac)
- [high] RBAC grants add to Entra ID consents, so to restrict the app to certain mailboxes you must remove the tenant-wide Mail.Read/Mail.ReadWrite consent in Entra; RBAC for Applications replaces Application Access Policies, and permission changes can take 30 minutes to 2 hours to apply because of caching (Test-ServicePrincipalAuthorization bypasses the cache). (https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac)
- [high] Well-known folder names work in place of folder ids whatever the mailbox locale: archive, clutter, conflicts, conversationhistory, deleteditems, drafts, inbox, junkemail, localfailures, msgfolderroot, outbox, recoverableitemsdeletions, scheduled, searchfolders, sentitems, serverfailures, syncissues. (https://learn.microsoft.com/en-us/graph/api/resources/mailfolder?view=graph-rest-1.0)
- [high] GET /users/{id}/mailFolders returns only the folders directly under the root (hidden ones only with includeHiddenFolders=true), with a default page size of 10; deeper folders must be listed per folder through .../mailFolders/{id}/childFolders. (https://learn.microsoft.com/en-us/graph/api/user-list-mailfolders?view=graph-rest-1.0) NOTE: The page says the call 'supports OData query parameters' but gives no example of $filter=displayName eq 'x'.
- [high] POST /users/{id}/mailFolders with {"displayName":"...","isHidden":false} creates a folder under the root and returns 201 Created with the mailFolder; child folders are created by POSTing to .../mailFolders/{id}/childFolders. (https://learn.microsoft.com/en-us/graph/api/user-post-mailfolders?view=graph-rest-1.0)
- [high] mailFolder has totalItemCount and unreadItemCount, which Microsoft recommends over queries like messages?$count=true&$filter=isread eq false because of their latency; this makes a cheap 'anything new?' check before polling. (https://learn.microsoft.com/en-us/graph/api/resources/mailfolder?view=graph-rest-1.0)
- [high] Message delta is per folder: GET /users/{id}/mailFolders/{id}/messages/delta, optionally with changeType=created|updated|deleted; supports $select, $top and $expand; $filter only as receivedDateTime ge|gt {value}; $orderby only as receivedDateTime desc; no $search. (https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0)
- [high] Applying $filter to a message delta query returns at most 5,000 messages, and page size is set with the 'Prefer: odata.maxpagesize={x}' header. (https://learn.microsoft.com/en-us/graph/delta-query-messages)
- [high] Query parameters must be sent only on the first delta request because Graph encodes them into the opaque @odata.nextLink ($skiptoken) and @odata.deltaLink ($deltatoken) URLs; the client keeps following nextLink until a deltaLink comes back, stores it (in a NAV table), and calls it at the next poll. (https://learn.microsoft.com/en-us/graph/delta-query-overview)
- [high] Deleted messages and messages moved out of the folder come back as {"id":...,"@removed":{"reason":"deleted"}}; read/unread changes and @removed entries are returned even when they don't match the initial $filter, and replays (the same change twice) can occur, so processing must be idempotent. (https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0)
- [high] Outlook (message/mailFolder) delta tokens have no fixed lifetime; they are evicted when an internal cache fills, and an expired token gives a 40X error with a code such as syncStateNotFound, which the client must handle by doing a full resync from a fresh delta request. (https://learn.microsoft.com/en-us/graph/delta-query-overview)
- [high] Delta can also return 410 Gone with a Location header holding a URL with an empty $deltatoken, which means the app must restart with a full synchronization. (https://learn.microsoft.com/en-us/graph/delta-query-overview)
- [high] Sending 'Prefer: IdType="ImmutableId"' on each request (it applies only to the request it is on) returns message and attachment ids that stay the same when the item moves to another folder in the same mailbox; they change only on a move to an archive mailbox or an export/re-import, and ids are case-sensitive. (https://learn.microsoft.com/en-us/graph/outlook-immutable-id)
- [high] Without ImmutableId, a message id changes when the message moves; delta nextLink/deltaLink URLs work with both id formats, and translateExchangeIds converts up to 1000 existing ids (sourceIdType restId -> targetIdType restImmutableEntryId). (https://learn.microsoft.com/en-us/graph/outlook-immutable-id)
- [high] POST /users/{id}/messages/{id}/move with body {"destinationId":"<folder id or well-known name>"} returns 201 Created and the moved message, which has a new id unless ImmutableId is used, because a move creates a new copy in the destination and removes the original. (https://learn.microsoft.com/en-us/graph/api/message-move?view=graph-rest-1.0)
- [high] PATCH /users/{id}/messages/{id} with {"isRead":true} returns 200 OK with the updated message (isRead and categories can be updated on received non-draft messages); DELETE /users/{id}/messages/{id} returns 204 No Content. (https://learn.microsoft.com/en-us/graph/api/message-update?view=graph-rest-1.0)
- [high] receivedDateTime, sentDateTime, createdDateTime and lastModifiedDateTime are ISO 8601 in UTC (example '2014-01-01T00:00:00Z'); bodyPreview is the first 255 characters of the body as text; uniqueBody is returned only when selected with $select=uniqueBody; internetMessageHeaders also needs $select. (https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0)
- [high] hasAttachments does not count inline attachments, so a message with only inline images has hasAttachments=false; inline content shows up as cid: src references in the HTML body. (https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0)
- [high] from is the mailbox owner the message was sent from and sender is the account that actually generated it (they differ for delegates or shared mailboxes); internetMessageId is the RFC 2822 Message-ID and is a stable duplicate key for NAV. (https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0) NOTE: Using internetMessageId as a duplicate key is a design suggestion.
- [high] GET /users/{id}/messages/{id}/$value returns the full MIME (.eml) content of the message, which can be saved as an .EML file and attached to ERP records. (https://learn.microsoft.com/en-us/graph/outlook-get-mime-message)
- [high] An attachment is a fileAttachment, itemAttachment (an attached contact, event or message) or referenceAttachment (a cloud link); each carries @odata.type, id, name, contentType, size (Int32 bytes), isInline and lastModifiedDateTime, and fileAttachment adds base64 contentBytes and contentId. (https://learn.microsoft.com/en-us/graph/api/attachment-get?view=graph-rest-1.0)
- [high] The documented sample response for GET /users/{id}/messages/{id}/attachments includes contentBytes for fileAttachments in the list, so without $select a list call can return all attachment content inline as base64. (https://learn.microsoft.com/en-us/graph/api/message-list-attachments?view=graph-rest-1.0) NOTE: The page says the call supports OData query parameters, but it was not verified whether $select can exclude contentBytes on the polymorphic attachment list.
- [high] GET .../messages/{id}/attachments/{aid}/$value returns raw bytes for a fileAttachment (in its original content type), MIME for an attached message, vCard for a contact and iCal for an event, and HTTP 405 for a referenceAttachment. (https://learn.microsoft.com/en-us/graph/api/attachment-get?view=graph-rest-1.0)
- [high] Properties of an attached item, including its nested attachments up to 30 levels deep, are returned with ?$expand=microsoft.graph.itemattachment/item. (https://learn.microsoft.com/en-us/graph/api/attachment-get?view=graph-rest-1.0)
- [high] Outlook limits are per app ID and mailbox: 10,000 API requests per 10 minutes, four concurrent requests, and 150 MB of upload (PATCH/POST/PUT) per 5 minutes; JSON batches send at most four requests to Outlook at a time. (https://learn.microsoft.com/en-us/graph/throttling-limits)
- [high] 429 means throttled and the client must wait before retrying; 503 may carry a Retry-After header for the delay; 504 is a gateway timeout; the code to branch on is error.code (and nested innererror.code), never error.message. (https://learn.microsoft.com/en-us/graph/errors)
- [high] Webhook change notifications need a publicly reachable HTTPS notificationUrl that echoes the validationToken as text/plain within 10 seconds and answers each notification within 3 seconds, and a non-public endpoint receives no notifications; an on-prem NAV 2016 service tier usually has no such endpoint, so delta or $filter polling is the practical choice. (https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks) NOTE: The conclusion that polling fits on-prem NAV better is our inference from the documented requirements.

**Open questions:**
- Can $select (for example $select=id,name,contentType,size,isInline) on GET /messages/{id}/attachments reliably leave out contentBytes? The docs only say OData query parameters are supported. Test this against a real tenant.
- No documented upper limit was found for downloading an attachment via /$value or a whole message via /messages/{id}/$value. The Exchange Online maximum message size (often cited as up to 150 MB) was not checked in this pass.
- Whether GET /users/{id}/mailFolders?$filter=displayName eq 'X' is supported was not confirmed by a doc example. Fallback: list with paging and compare displayName on the client side.
- Can several preferences go in one Prefer header separated by commas (for example IdType="ImmutableId", outlook.body-content-type="text"), or must they be separate Prefer headers? Not verified. Test both ways with HttpClient.
- The exact HTTP status (400 vs 404 vs 410) and error.code (syncStateNotFound, syncStateInvalid, resyncRequired) for expired message delta tokens are not tabulated. The overview only says '40X-series ... such as syncStateNotFound'. Treat any 4xx on a stored deltaLink plus 410 as a reason for a full resync.
- The docs give no maximum for 'Prefer: odata.maxpagesize' on message delta, and $top on delta 'can vary'.
- How time-zone suffixes and fractional seconds in $filter receivedDateTime literals are handled (e.g. 2026-10-12T08:00:00Z vs 2026-10-12T08:00:00.000Z) was not verified beyond the documented UTC 'Z' output format.
- Whether Mail.ReadBasic.All allows hasAttachments and listing attachment metadata (without content) was not verified.

**Recommendations:**
- Base polling on delta per folder: first call GET /users/{mbx}/mailFolders/inbox/messages/delta?changeType=created&$select=id,internetMessageId,subject,from,sender,toRecipients,ccRecipients,receivedDateTime,hasAttachments,isRead,bodyPreview,conversationId with Prefer: odata.maxpagesize=50 and Prefer: IdType="ImmutableId". Store the final @odata.deltaLink in a NAV setup or table field (BLOB/Text 2048+, since the URLs are long). On syncStateNotFound, any 4xx on the deltaLink, or 410, drop the link and resync, falling back to receivedDateTime ge <last processed>.
- Offer a simpler non-delta mode for NAV users: GET .../mailFolders/{folder}/messages?$filter=receivedDateTime ge {lastUtc} and isRead eq false&$orderby=receivedDateTime asc&$top=50&$select=..., following @odata.nextLink, then PATCH isRead=true or move to a 'Processed' folder. Keep receivedDateTime first in $filter to avoid InefficientFilter.
- Always send Prefer: IdType="ImmutableId" so ids saved in NAV survive moves to 'Processed' or 'Error' folders, and treat ids as case-sensitive. In C/AL use a Text field of at least 250 characters or a BLOB rather than Code, because Code fields uppercase values.
- Use internetMessageId as the duplicate key in NAV, because delta can replay changes and moves create new copies.
- Fetch attachments in two steps: list metadata (try $select without contentBytes), then stream each fileAttachment with GET .../attachments/{aid}/$value straight to a FileStream or blob upload instead of base64 in JSON. This keeps large files out of DataContractJsonSerializer and out of NAV memory. Skip referenceAttachment (405) and use /$value MIME for itemAttachment.
- Offer DownloadMessageMime(messageId, path) through /messages/{id}/$value so NAV can archive the original .eml.
- Limit to at most 4 concurrent requests per mailbox (for example a SemaphoreSlim per mailbox in the DLL), and honor Retry-After on 429/503 with exponential backoff.
- Keep the C/AL surface flat and DotNet-interop-friendly: a MailboxReader facade with Open(tenant, clientId, secret, mailbox), Poll(folder) returning a count, Next()/Current properties made of primitive strings, DateTime and Int32, SaveAttachment(index, path), MarkRead(), MoveTo(folderNameOrId), EnsureFolder(name) returning an id, plus a GetDeltaState()/SetDeltaState(text) pair so NAV owns persistence. Avoid generics, events and async in the public API.
- Set permissions as Mail.ReadWrite (application) for read+mark+move, plus the existing Mail.Send. Document the Exchange Online 'Application Mail.ReadWrite' RBAC assignment with a management scope, and say that the tenant-wide Entra consent must then be removed for the scoping to take effect.
- Document why polling instead of webhooks: on-prem NAV usually has no public HTTPS endpoint that can answer validation within 10 seconds and notifications within 3 seconds.

## Azure Blob Storage REST

- [high] As of 2026-09-23, Microsoft lists 2026-04-06 as the latest fully deployed Azure Storage service version. 2026-06-06 and 2026-10-06 are enabled globally except in a few tenants in useast2euap and uscentraleuap, and the latest GA SDKs default to 2026-10-06. Sending a version that is not deployed in the account's region can cause an x-ms-version mismatch error. (https://learn.microsoft.com/en-us/rest/api/storageservices/versioning-for-the-azure-storage-services) NOTE: For a library that targets many regions, a conservative pin such as 2025-xx or 2026-04-06 is safer than the newest version. It should be a configurable property.
- [high] The x-ms-version value uses the format YYYY-MM-DD. Every Blob request that does not use a SAS must send x-ms-version, unless the account has set a default version through Set Blob Service Properties. (https://learn.microsoft.com/en-us/rest/api/storageservices/versioning-for-the-azure-storage-services)
- [high] To get a token for Azure Storage, use the resource ID https://storage.azure.com/ (with v2 client credentials the scope is https://storage.azure.com/.default). Send the token as 'Authorization: Bearer <token>' together with x-ms-version 2017-11-09 or later. (https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-azure-active-directory) NOTE: The doc names the resource ID https://storage.azure.com/. The '/.default' suffix follows the standard Microsoft identity platform v2 rule; this page does not spell it out.
- [high] Without a valid token, Blob service versions 2019-12-12 and later return 401 with the header 'WWW-Authenticate: Bearer authorization_uri=https://login.microsoftonline.com/<tenant_id>/oauth2/authorize resource_id=https://storage.azure.com' and the error code NoAuthenticationInformation. (https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-azure-active-directory)
- [high] The least-privileged built-in role for Put Blob, Put Block, Put Block List and Delete Blob is 'Storage Blob Data Contributor'. Get Blob and Get Blob Properties need only 'Storage Blob Data Reader'. Get User Delegation Key needs 'Storage Blob Delegator' (action generateUserDelegationKey/action), assigned at storage account, resource group or subscription scope. (https://learn.microsoft.com/en-us/rest/api/storageservices/put-blob) NOTE: Also stated on the get-blob, delete-blob and get-user-delegation-key reference pages.
- [high] For Blob service version 2009-09-19 and later, the Shared Key StringToSign is: VERB + "\n" + Content-Encoding + "\n" + Content-Language + "\n" + Content-Length + "\n" + Content-MD5 + "\n" + Content-Type + "\n" + Date + "\n" + If-Modified-Since + "\n" + If-Match + "\n" + If-None-Match + "\n" + If-Unmodified-Since + "\n" + Range + "\n" + CanonicalizedHeaders + CanonicalizedResource. The VERB is uppercase. (https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-shared-key)
- [high] From version 2015-02-21 onward, the Content-Length line must be an empty string when the request body length is zero; only 2014-02-14 and earlier used '0'. When you send x-ms-date, leave the Date line empty. (https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-shared-key)
- [high] To build CanonicalizedHeaders: take every header starting with x-ms- (including x-ms-date), lowercase the names, sort them lexicographically ascending, collapse linear whitespace in values to a single space, trim around the colon, and end each 'name:value' with \n. Since 2016-05-31, headers with empty values are kept as 'name:\n'. (https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-shared-key)
- [high] To build CanonicalizedResource: '/' + account name + the encoded URI path (no query). Then add each query parameter with a lowercased name, sorted ascending by name and URL-decoded, as '\nname:value'. A parameter with several values gets its values sorted and comma-joined. Example: /myaccount/mycontainer\ncomp:list\ninclude:metadata,snapshots,uncommittedblobs\nrestype:container. (https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-shared-key)
- [high] Signature = Base64(HMAC-SHA256(UTF8(StringToSign), Base64.decode(accountKey))). The header is 'Authorization: SharedKey <AccountName>:<Signature>'. The request time must be within 15 minutes of the server time or the service returns 403. Each header in the signature may appear only once, otherwise the service returns 400. (https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-shared-key)
- [high] When authorizing against the storage emulator, the account name appears twice in CanonicalizedResource, for example /devstoreaccount1/devstoreaccount1/container/blob, because the account name is also part of the URL path. (https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-shared-key) NOTE: The doc says 'the account name will appear twice'. The exact string above is inferred from the path rule.
- [high] Date and x-ms-date values use RFC 1123 in UTC/GMT, e.g. 'Sun, 06 Nov 1994 08:49:37 GMT'. In .NET, DateTime.UtcNow.ToString("R") produces this format. (https://learn.microsoft.com/en-us/rest/api/storageservices/representation-of-date-time-values-in-headers) NOTE: The format is from the doc. The .NET "R" specifier is standard .NET knowledge and is not stated on this page.
- [high] Put Blob is 'PUT https://<acct>.blob.core.windows.net/<container>/<blob>' with the header 'x-ms-blob-type: BlockBlob' and a Content-Length. If no type is given, the default content type is application/octet-stream. Success returns 201 Created with ETag, Last-Modified, Content-MD5 and x-ms-content-crc64. An existing blob and its metadata are overwritten. (https://learn.microsoft.com/en-us/rest/api/storageservices/put-blob)
- [high] Size limits by version. 2019-12-12 and later: Put Blob single write up to 5,000 MiB, Put Block up to 4,000 MiB, blob up to about 190.7 TiB (50,000 blocks). 2016-05-31 through 2019-07-07: 256 MiB, 100 MiB and about 4.75 TiB. Earlier versions: 64 MiB, 4 MiB and about 195 GiB. Uploads over the limit return 413. (https://learn.microsoft.com/en-us/rest/api/storageservices/put-block)
- [high] Put Block is 'PUT <blob-url>?comp=block&blockid=<id>'. The blockid must be valid Base64 of at most 64 bytes before encoding, and it must be URL-encoded in the query. All block IDs for one blob must have the same length, otherwise the service returns 400. Success returns 201 Created. A missing Content-Length returns 411. (https://learn.microsoft.com/en-us/rest/api/storageservices/put-block)
- [high] A block blob can hold at most 50,000 committed blocks and 100,000 uncommitted blocks; going over returns 409 RequestEntityTooLargeBlockCountExceedsLimit. Uncommitted blocks are garbage-collected after a week with no successful Put Block or Put Block List, or immediately when Put Blob is called. (https://learn.microsoft.com/en-us/rest/api/storageservices/put-block)
- [high] Put Block List is 'PUT <blob-url>?comp=blocklist' with the XML body '<?xml version="1.0" encoding="utf-8"?><BlockList><Latest>base64-id</Latest>...</BlockList>'. The elements Committed, Uncommitted and Latest select which list each ID is looked up in. Success returns 201 Created. Set the blob content type with x-ms-blob-content-type; the default is application/octet-stream. Properties and metadata are overwritten. (https://learn.microsoft.com/en-us/rest/api/storageservices/put-block-list)
- [high] Content-MD5 and x-ms-content-crc64 (supported from 2019-02-02) on Put Blob, Put Block and Put Block List are checked against the transmitted body; a mismatch returns 400, and sending both returns 400. On Put Block List the hash covers the XML body, not the blob. For Put Blob without Content-MD5, the service computes and stores an MD5 (2012-02-12 and later). (https://learn.microsoft.com/en-us/rest/api/storageservices/put-blob)
- [high] Get Blob is 'GET <blob-url>'. A full read returns 200 and a ranged read returns 206. Ranges use 'Range' or 'x-ms-range' with 'bytes=start-end' (all versions) or 'bytes=start-' (2011-08-18 and later); x-ms-range wins if both are sent. A start offset beyond the blob length returns 416. The service allows two minutes per MiB before timing out. (https://learn.microsoft.com/en-us/rest/api/storageservices/specifying-the-range-header-for-blob-service-operations)
- [high] 'x-ms-range-get-content-md5: true' or 'x-ms-range-get-content-crc64: true' (2019-02-02 and later) return a hash for a range of 4 MiB or less. Using either without a Range, or with a range over 4 MiB, returns 400. Response headers include Content-Length, Content-Type, Content-Range, ETag, x-ms-blob-type and x-ms-meta-*. (https://learn.microsoft.com/en-us/rest/api/storageservices/get-blob)
- [high] Get Blob Properties is 'HEAD <blob-url>', returns 200 with no body, and exposes Content-Length (the blob size), Content-Type, ETag, Last-Modified, Content-MD5, x-ms-blob-type and the metadata as x-ms-meta-* headers. (https://learn.microsoft.com/en-us/rest/api/storageservices/get-blob-properties)
- [high] Error bodies have the shape '<?xml version="1.0" encoding="utf-8"?><Error><Code>string</Code><Message>string</Message></Error>' and may carry extra elements. From version 2017-07-29, the error code is also returned in the 'x-ms-error-code' response header. This header is the only way to read the code on a HEAD 404, because HEAD responses have no body. (https://learn.microsoft.com/en-us/rest/api/storageservices/status-and-error-codes2) NOTE: That HEAD has no body follows from HTTP semantics and the Get Blob Properties page ('Response body: None').
- [high] Delete Blob is 'DELETE <blob-url>' and returns 202 Accepted. If the blob has snapshots, send 'x-ms-delete-snapshots: include' (or 'only'), otherwise the service returns 409. When soft delete is enabled, the blob is kept for the retention period. From 2013-08-15, uncommitted blobs can be deleted. (https://learn.microsoft.com/en-us/rest/api/storageservices/delete-blob)
- [high] List Blobs is 'GET https://<acct>.blob.core.windows.net/<container>?restype=container&comp=list' with optional prefix, delimiter, marker, maxresults (default and maximum 5,000; 0 or less returns 400) and include parameters. Keep calling with marker=<NextMarker> until NextMarker is empty. The service can return fewer results than maxresults together with a non-empty NextMarker. (https://learn.microsoft.com/en-us/rest/api/storageservices/list-blobs)
- [high] The List Blobs response XML is EnumerationResults (attributes ServiceEndpoint and ContainerName) > Prefix/Marker/MaxResults/Delimiter, then Blobs > Blob > Name + Properties (Creation-Time, Last-Modified, Etag, Content-Length, Content-Type, Content-MD5, BlobType, AccessTier, ...) + Metadata. BlobPrefix > Name entries appear when a delimiter is used, followed by NextMarker. (https://learn.microsoft.com/en-us/rest/api/storageservices/list-blobs)

**Open questions:**
- The service SAS page (updated 2026-03-26) only documents the StringToSign up to the 2020-12-06 format. I could not confirm whether newer sv values such as 2026-04-06 add fields like srh/srq to the service SAS, as they do for the user delegation SAS. - The Entra token scope and authority for sovereign clouds are not verified. US Gov is probably login.microsoftonline.us and China login.chinacloudapi.cn, and it is unknown whether https://storage.azure.com/.default stays the same there.
- Which x-ms-version Azurite currently accepts depends on the installed Azurite release. A newer x-ms-version may need --skipApiVersionCheck; the GitHub release notes were not checked.
- Whether the 2 GiB emulator blob-size limit applies to Azurite or only to the legacy Storage Emulator was not verified.
- The CRC64 polynomial and encoding for x-ms-content-crc64 (Azure's custom CRC64 and its byte order) are not documented in the pages I read. Use Content-MD5 for a zero-dependency .NET 4.6.2 implementation.
- There is no official guidance on whether HttpClient on .NET Framework 4.6.2 adds or modifies headers that are part of the signature, such as Content-Type charset or Content-Length. Test this against Azurite.
- The user delegation SAS query parameter names (skoid, sktid, skt, ske, sks, skv, ses, etc.) are mapped from field names in the doc's tables, but I only read the StringToSign sections verbatim, not the parameter-name tables.

**Recommendations:**
- Make x-ms-version a configurable constant. Default to a widely deployed version (for example 2025-11-05, or 2026-04-06 once confirmed for the target regions) and never below 2019-12-12, so the 5,000 MiB Put Blob and 4,000 MiB block limits apply.
- Upload strategy: use a single Put Blob up to a configurable threshold (for example 32-64 MiB, given NAV memory limits). Above that, stream fixed-size blocks (for example 8 MiB) with Put Block and fixed-length Base64 IDs, e.g. Base64 of a zero-padded 6-digit index, then commit with Put Block List using <Latest>. Retry each block on its own.
- Add three auth modes behind one interface. (1) Bearer: reuse the existing client-credentials token code with scope https://storage.azure.com/.default. (2) SharedKey: account name + key with the exact StringToSign above. (3) SAS URL: append the blob name before the query, send no Authorization header. Expose one connection-string-like setup so NAV C/AL only calls something like SetupAzureBlob(account, container, authMode, secret).
- Use HEAD (Get Blob Properties) for exists/size checks. Treat a 404 with x-ms-error-code BlobNotFound as 'not found' and return a boolean rather than throwing into C/AL.
- Parse List Blobs XML with XmlDocument/XDocument (no DataContractJsonSerializer). Loop on NextMarker inside the library and give NAV a simple enumerator or count+index accessor.
- Download large blobs with ranged GETs (x-ms-range bytes=start-end) in chunks written to a FileStream or temp file, so the whole blob is never held in memory in the NAV service tier.
- Build Shared Key unit tests from the doc examples, then run integration tests against Azurite in Docker on macOS: http://127.0.0.1:10000/devstoreaccount1 with the well-known key. Remember that CanonicalizedResource contains the account name twice there.
- On .NET Framework 4.6.2, set ServicePointManager.SecurityProtocol to include TLS 1.2 and set HttpClient.Timeout per operation, keeping in mind the service allows 10 minutes per MiB for Put Blob and 2 minutes per MiB for Get Blob.

## Amazon S3 / SigV4 / S3-compatible

- [high] The S3 SigV4 canonical request is exactly '<HTTPMethod>\n<CanonicalURI>\n<CanonicalQueryString>\n<CanonicalHeaders>\n<SignedHeaders>\n<HashedPayload>', where each canonical header line itself ends in '\n', so an empty query string still produces an empty line and a blank line always separates the headers block from SignedHeaders. (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html) NOTE: The docs.aws.amazon.com/AmazonS3/latest/API/sig-v4-header-based-auth.html URL now 302-redirects to the API index. The identical page is still served by the docs.aws.eu mirror, which is where it was read.
- [high] UriEncode must leave only A-Z, a-z, 0-9, '-', '.', '_' and '~' unencoded and percent-encode every other UTF-8 byte with uppercase hex (e.g. %1A), with space as %20 (never '+'), and '/' encoded everywhere except in the object key name; AWS recommends writing your own UriEncode because platform encoders differ. (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html) NOTE: Example from the doc: key 'test$file.text' becomes canonical URI '/test%24file.text'.
- [high] For S3 you must NOT normalize URI paths (e.g. 'my-object//example//photo.user' must stay as-is), and the S3 key is encoded once (the doc describes a single UriEncode of the absolute path and shows no double-encoding). (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html) NOTE: The page itself says 'do not normalize'. The single-encode claim follows from the S3 examples ('/test%24file.text'); the page has no explicit sentence saying 'do not double-encode'.
- [high] In the canonical query string, each parameter name and value is UriEncoded individually, the parameters are sorted alphabetically by key name after encoding, and a subresource with no value is written as 'name=' (e.g. 'lifecycle=', 'uploads='). (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html)
- [high] Canonical headers are written as Lowercase(name)+':'+Trim(value)+'\n', sorted by name, and must include host, Content-MD5 if present, and every x-amz-* header sent (including x-amz-security-token for temporary credentials); signing x-amz-content-sha256 is optional because S3 uses its value as the payload hash. (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html) NOTE: In practice, sign host;x-amz-content-sha256;x-amz-date (plus range, content-type and so on) as the AWS examples do.
- [high] SignedHeaders is an alphabetically sorted, semicolon-separated list of the lowercase header names that appear in CanonicalHeaders, e.g. 'host;range;x-amz-content-sha256;x-amz-date'. (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html)
- [high] The x-amz-content-sha256 header is required on all SigV4 header-authenticated S3 requests; its value is the hex SHA-256 of the body (empty body = e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855) or the literal 'UNSIGNED-PAYLOAD', and the same value is used as HashedPayload in the canonical request. (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html)
- [high] Allowed x-amz-content-sha256 values are the actual payload hash (single-chunk only), UNSIGNED-PAYLOAD (single unsigned chunk), STREAMING-UNSIGNED-PAYLOAD-TRAILER, STREAMING-AWS4-HMAC-SHA256-PAYLOAD, STREAMING-AWS4-HMAC-SHA256-PAYLOAD-TRAILER, and two STREAMING-AWS4-ECDSA-P256-SHA256-* (SigV4A) variants; trailers additionally require an x-amz-trailer header. (https://docs.aws.eu/AmazonS3/latest/developerguide/sigv4-auth-using-authorization-header.html) NOTE: The page does not state that UNSIGNED-PAYLOAD is restricted to HTTPS. Streaming chunked signing also requires x-amz-decoded-content-length (see the sigv4-streaming page on the same mirror). For a zero-dependency client, single-chunk UNSIGNED-PAYLOAD or a hashed body per multipart part is far simpler.
- [high] The timestamp is UTC ISO 8601 basic format yyyyMMdd'T'HHmmss'Z' (e.g. 20130524T000000Z); if both Date and x-amz-date are present, x-amz-date takes precedence, and signed portions of a request are valid only within 15 minutes of that timestamp. (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-authenticating-requests.html) NOTE: The format string is from sigv4-query-string-auth, and the x-amz-date precedence is from sigv4-auth-using-authorization-header, both on the same docs.aws.eu mirror.
- [high] StringToSign = 'AWS4-HMAC-SHA256\n' + timestamp + '\n' + scope + '\n' + Hex(SHA256(CanonicalRequest)), where scope = YYYYMMDD/<region>/s3/aws4_request (e.g. 20130606/us-east-1/s3/aws4_request) and the scope date must equal the date used for the signing key. (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html)
- [high] The signing key is derived as DateKey=HMAC-SHA256("AWS4"+secret, YYYYMMDD); DateRegionKey=HMAC-SHA256(DateKey, region); DateRegionServiceKey=HMAC-SHA256(DateRegionKey, "s3"); SigningKey=HMAC-SHA256(DateRegionServiceKey, "aws4_request"), and the signature is lowercase hex of HMAC-SHA256(SigningKey, StringToSign). (https://docs.aws.eu/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html)

**Open questions:**

If it does, the wire path will not match the signed canonical URI. This needs an empirical test, and possibly the dontEscape or UriSyntax workaround, on .NET Framework specifically.

- Do Wasabi and Hetzner reject x-amz-checksum-* headers or the newer default integrity checksums? This is unverified.
- Which replacement for the minio/minio docker image do we standardize on for local macOS testing (SeaweedFS, RustFS, Garage, LocalStack, S3Mock)? Their default credentials and path-style behavior were not verified.

**Recommendations:**
- Use the five AWS vectors (GET object with Range, PUT test$file.text, GET ?lifecycle, ListObjects max-keys/prefix, presigned GET) verbatim as unit tests. All five were reproduced locally in Python with matching signatures. Test the canonical-request string, its hash and the signature separately so failures are easy to localize.
- Implement a custom UriEncode(string, encodeSlash) over UTF-8 bytes with uppercase hex. Do not use Uri.EscapeDataString or HttpUtility.UrlEncode ('+' for space, lowercase hex). Encode each key segment once and never normalize the path.
- Always send x-amz-content-sha256 and x-amz-date and sign host;x-amz-content-sha256;x-amz-date (plus range, content-type, x-amz-security-token when present). Use the real SHA-256 for small bodies and per-part bodies; reserve UNSIGNED-PAYLOAD for streamed large single PUTs over HTTPS.
- Skip aws-chunked streaming signatures (STREAMING-*) entirely. For large attachments use multipart with a configurable part size (default 8-16 MiB, minimum 5 MiB, at most 10,000 parts) and hash each part. Collect ETags from the UploadPart response header, send CompleteMultipartUpload in ascending order, parse the 200 response body for <Error>, and call AbortMultipartUpload on failure.
- Expose a simple NAV-facing configuration: Endpoint (URL), Region, Bucket, AccessKey, SecretKey, optional SessionToken, ForcePathStyle (bool). Default ForcePathStyle=true for custom endpoints, R2, Hetzner, Wasabi and local test servers, and for any bucket containing '.'. Default the region to 'auto' for R2 and 'us-east-1' for local test servers.
- Surface S3 errors to C/AL as a flat result (HttpStatus, Code, Message, RequestId) parsed from the <Error> XML. HEAD has no body, so map 404 and 403 by status alone. Treat RequestTimeTooSkewed as a hint to check the NAV server clock (15-minute window).
- Provide a GetPresignedUrl(key, expirySeconds <= 604800) method so NAV can hand out download links without streaming bytes through C/AL.
- For local testing on macOS, do not depend on the minio/minio docker image (it was not pullable on 2026-10-12). Pick a verified alternative (e.g. SeaweedFS, RustFS, Garage, LocalStack) and document its credentials in the repo test README after verifying them.

**Recommendations:**
- Design the polling entry point as a codeunit with TableNo=472 that reads Rec."Parameter String" (e.g. a mailbox setup code, max 250 characters) in OnRun and lets errors surface via ERROR(). The standard Job Queue then retries 'Maximum No. of Attempts to Run' times with 'Rerun Delay (sec.)' and logs to Table 474. No custom error-logging plumbing is needed beyond per-message status in your own tables.
- Add a 'Schedule polling' action on the setup card that builds a Job Queue Entry (Object Type to Run=Codeunit, Recurring Job=TRUE, No. of Minutes between Runs, Run on Mondays..Sundays) and calls Codeunit 453 EnqueueJobQueueEntry, so users never have to edit Job Queue entries by hand.
- Store secrets (client secret, Azure storage key or SAS, S3 secret key) with the Table 1260 / Page 1260 pattern: a GUID 'Password Key' with TableRelation to Service Password 1261, SavePassword/GetPassword/HasPassword/DeletePassword, and a masked page variable showing 'Password Dots'.
- Use a singleton setup table plus a Card page with InsertAllowed=No and OnOpenPage `IF NOT GET THEN BEGIN INIT; INSERT; END;`. Add a list page of received messages (Subject/From as Text250, Body and attachments as BLOB) with an attachments subpage or FactBox.
- Keep all DotNet variables server-side (no RUNONCLIENT), since job-queue runs have no client. Pass C/AL InStream/OutStream straight to DLL methods typed System.IO.Stream (e.g. UploadBlob(Stream content), DownloadTo(Stream target)), which standard NAV 2016 code proves works in both directions.
- For large attachments, have the DLL stream Graph content (/$value or range requests) directly into a C/AL OutStream from TempBlob.Blob.CREATEOUTSTREAM or straight to Blob/S3, and keep only metadata plus the object URL/key in NAV, so multi-hundred-MB data does not pass through C/AL Text.
- After writing BLOBs, INSERT or MODIFY before CALCFIELDS, because of the NAV 2016 behaviour change. Never CALCFIELDS an uninserted record. TempBlob in 2016 has no WriteAsText, so use CREATEOUTSTREAM + WRITETEXT.
- Expose .NET results as simple types (String, Int32, Int64 to BigInteger, Boolean, DateTime, Guid) and collections as List<T>/arrays usable with FOREACH. Also provide Count + GetItem(int) methods as a safe fallback, avoid Nullable<T>, and return DateTime.MinValue-safe values (map to 0DT) because C/AL DateTime starts in 1753.
- Return timestamps as System.DateTime from the DLL and assign them directly to C/AL DateTime instead of parsing ISO strings in C/AL. If strings are used, test EVALUATE(..., 9) with Graph's 'Z' and 7-digit fractional seconds first.
- For web-client downloads of attachments, use FileManagement.BLOBExport(TempBlob, FileName, TRUE) or DOWNLOADFROMSTREAM. Avoid DownloadToFile/ClientTempFileName, which need client file access.
- Raise integration events in your NAV codeunit (exported as `[Integration]` or `[Integration(TRUE)]` for IncludeSender), e.g. OnAfterMailReceived(VAR InboxMessage : Record ...), so partners can hook processing without modifying your code. Do not rely on GlobalVarAccess in NAV 2016.
- A SingleInstance codeunit with a global DotNet client can cache tokens within one interactive session. Each job-queue run is a fresh STARTSESSION, though, so the DLL should handle token caching itself (static cache), or the polling run should fetch a token once per run.

## Follow-up (nav-cal)

*Question:* Where should large attachments end up? Option 1: inside a NAV BLOB field, copied through the C/AL InStream/OutStream on the NAS. Option 2: streamed by the DLL straight from Graph /$value to Azure Blob or S3, with NAV keeping only metadata and the container/key or URL. If both are wanted, what size threshold switches between them?

- [high] Appending /$value to a message attachment URL (GET /users/{id|upn}/messages/{id}/attachments/{id}/$value) returns the raw bytes of a fileAttachment, and for itemAttachments returns MIME (message), vCard (contact) or iCal (event). (https://learn.microsoft.com/en-us/graph/api/attachment-get?view=graph-rest-1.0)
- [high] Requesting /$value of a referenceAttachment (cloud link) returns HTTP 405, so link-type attachments carry no bytes to store anywhere and need a separate code path (metadata only). (https://learn.microsoft.com/en-us/graph/api/attachment-get?view=graph-rest-1.0)
- [high] Application permission Mail.Read is the least-privileged permission for getting a message attachment, including /$value. (https://learn.microsoft.com/en-us/graph/api/attachment-get?view=graph-rest-1.0)
- [high] Microsoft says getting an attachment is not technically limited by size, but getting a large attachment as base64 (contentBytes) hurts API performance; for large attachments it recommends /$value for content and $select (without contentBytes) for metadata. (https://learn.microsoft.com/en-us/graph/outlook-large-attachments)
- [high] fileAttachment.size is Int32 (bytes) and contentBytes is Edm.Binary (base64), so the size maps cleanly to a C/AL Integer field. (https://learn.microsoft.com/en-us/graph/api/resources/fileattachment?view=graph-rest-1.0)
- [high] In Exchange Online the default maximum message size is 35 MB for sending and 36 MB for receiving, admins can set a custom limit from 1 MB to 150 MB, and the limit includes attachments; the file attachment size limit for Outlook is 150 MB. (https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits)
- [high] Messages that leave Microsoft datacenters get roughly 33% encoding overhead, so the effective maximum for internet mail is 112 MB, which means a single attachment in an Exchange Online mailbox realistically cannot be several hundred MB; 150 MB is the ceiling. **Recommendations:**
- Decision: support both options with a size threshold, and make object storage the default destination when a storage account is configured. Exchange Online limits a message to 150 MB (35/36 MB by default), so 'several hundred MB' cannot come from mail; the worst case to design for is about 150 MB per attachment.
- Threshold: send attachments whose Graph 'size' (Int32) is at or below a configurable 'Max BLOB Size (KB)' to the NAV BLOB, and stream larger ones from the DLL to Azure or S3. Suggested default: 4 MB, matching Graph's ~3-4 MB small/large boundary and its 4 MB chunk guidance. Settings 0 = always object storage and 153600 KB = always BLOB, the latter only if no storage is configured. The 4 MB value is an engineering choice, not a documented limit; confirm it with a NAS load test.
- If no storage is configured, still use the BLOB but cap it: anything over the cap is recorded as metadata only with status 'Skipped - too large', so the job queue never takes an unbounded MemoryStream. Microsoft says BLOB streams typically use MemoryStreams, so a 150 MB attachment can sit in NAS memory more than once.
- DLL API, small path: DownloadAttachmentToStream(mailbox, messageId, attachmentId, OutStream) called from C/AL with the BLOB's OutStream. The DLL uses GET .../$value with HttpCompletionOption.ResponseHeadersRead and copies in 81920-byte chunks with its own CancellationToken timeout, because HttpClient.Timeout stops covering the call once headers arrive. It never reads contentBytes (base64).
- DLL API, large path: UploadAttachmentToStorage(mailbox, messageId, attachmentId, storageProfileCode) returns a small result object with Text/BigInteger properties (Provider, Container/Bucket, Key, Url, ETag, Size, Sha256/MD5) that C/AL copies into the attachment table. No stream crosses the C/AL boundary.
- Large-path transfer: read Graph /$value into one reused 8 MiB buffer and send each buffer as an Azure Put Block (fixed-length Base64 block IDs, then Put Block List with x-ms-blob-content-type and x-ms-meta-* for the message and attachment IDs) or as an S3 UploadPart. 8 MiB is above the S3 5 MiB part minimum, gives at most ~19 parts for 150 MB, keeps memory at about one buffer, and allows retrying a single chunk.
- Azure auth: reuse the existing client-credentials token code with resource/scope https://storage.azure.com/.default, x-ms-version 2019-12-12 or later, and the Storage Blob Data Contributor role. Implement Shared Key or SAS only if customers ask for it. Implement S3 SigV4 only after verifying the signing spec, which I could not read.
- NAV table design: 'Mail Attachment' table with Entry No., Message Entry No., Graph Attachment Id (Text 250+), Name, Content Type, Size (Integer), Is Inline, Attachment Type (File/Item/Reference), Storage Location (Option: BLOB, Azure Blob, S3, None), Content (BLOB, filled only when Storage Location = BLOB), Storage Profile Code, Container/Bucket, Object Key (Text 1024 or BigText), ETag, Hash, Status, Error Text. Use a separate 'Storage Profile' setup table (provider, account/endpoint, container, prefix, tenant/client, secret reference, Max BLOB Size).
- For NAV usability, wrap everything in one codeunit with functions such as ImportAttachments(MessageEntryNo) that applies the threshold automatically, and OpenAttachment/DownloadAttachment(EntryNo) that hides whether the bytes are in the BLOB or in storage. For storage, call a DLL DownloadFromStorageToFile(tempPath) and then use DOWNLOAD/HYPERLINK, so users never see container or key logic.
- Job queue safety: process one attachment per DLL call, COMMIT after each attachment, keep within the per-mailbox limit of 4 concurrent Graph requests, and honor Retry-After on 429. Record failures on the attachment row instead of raising ERROR, so one bad 150 MB file doesn't roll back the whole poll run.
- Handle referenceAttachment (/$value returns 405) as metadata only, and itemAttachment (/$value returns MIME/.eml) by the same size rule as file attachments.

**Recommendations:**
- Make the post-processing action a per-mailbox setup option (Option field: None, MarkAsRead, MoveToFolder, Delete). Default to MoveToFolder with Processed and Error subfolders: the source folder then acts as a visible work queue and the Error folder gives NAV admins a place to retry. It requires Mail.ReadWrite or the Exchange role 'Application Mail.ReadWrite'.
- Offer a read-only option (action None) for customers who refuse write access: it uses delta with changeType=created on one folder, Mail.Read or 'Application Mail.Read', and dedupe by internetMessageId and the immutable id. Do not make it the default, because it depends on deltaLink state with an unspecified lifetime.
- Do not build a $filter=isRead eq false mode as the primary mechanism: users who open the mail in Outlook flip isRead and the poller silently misses it, and delta with changeType=created never reports isRead changes anyway. If MarkAsRead is offered, combine it with a receivedDateTime watermark and dedupe, not isRead alone.
- For the default MoveToFolder mode, use plain list polling (GET /users/{upn}/mailFolders/{id}/messages?$filter=receivedDateTime ge {watermark minus safety margin}&$orderby=receivedDateTime asc&$top=N&$select=...), not delta. The folder only holds unprocessed mail, so no deltaLink state is needed, and the move-out would only produce @removed noise in delta.
- Always send Prefer: IdType="ImmutableId" on list, get, attachment and move calls, so the id stored in NAV survives the move to Processed/Error. Store it with case-sensitive comparison (for example as a hash or in a Text field without case folding).
- Write a NAV log/dedupe row (immutable id, internetMessageId, receivedDateTime, status) and COMMIT before calling move or PATCH. Then a crash between the NAV commit and the Graph call leads to a harmless re-skip instead of a duplicate import or a lost mail.
- In delta mode, store the full @odata.deltaLink URL in a BLOB and replace it only after all nextLink pages are consumed. On 410 Gone or an error code of syncStateNotFound, discard it and restart with a fresh initial request bounded by $filter=receivedDateTime ge {last imported receivedDateTime}, relying on dedupe to absorb overlap and staying under the 5,000-message filter cap.
- In delta mode, skip entries that carry @removed and entries with no receivedDateTime or internetMessageId (update-only noise), and treat every created entry as possibly replayed.
- Resolve the Processed and Error folders by displayName under the source folder once (create them if missing), cache their ids in the setup table, and re-resolve on 404 instead of hard-coding ids.
- Document both admin paths in the setup page help: the Entra ID application permission (Mail.Read or Mail.ReadWrite, plus Mail.Send already in use), or the scoped Exchange RBAC roles via New-ManagementRoleAssignment. Warn that an unscoped Entra consent nullifies the scoping and that RBAC changes can take up to 2 hours to apply.

**Recommendations:**

- Add a defensive guard in the .NET layer. Before deserializing a metadata response, check the Content-Length or stream length, or scan for a contentBytes key, and fail loudly if it is present. Microsoft documents that unsupported query options can fail silently.
- Prefer the per-message attachments?$select= call over $expand=attachments($select=...) on message list or poll calls. Branch on type: fileAttachment gives raw bytes, itemAttachment gives MIME (.eml/.ics/.vcf), and referenceAttachment gives 405, so store only its metadata.

- Follow @odata.nextLink defensively on the attachments collection, treating it as an opaque URL, even though paging of this collection is not documented.
- Ship an integration self-test command (for example, MailGraph.SelfTest) that sends a message with an attachment over 3 MB to a test mailbox, lists it with the metadata $select, and asserts the response is under a few KB with no contentBytes key. This settles the open question per tenant.

(https://learn.microsoft.com/en-us/dotnet/fundamentals/runtime-libraries/system-uri) NOTE: Escaped dots get unescaped either by the V2 UnEscapeDotsAndSlashes flag or, in V3, by the IRI path, because %2E is an escaped unreserved character.

(https://github.com/microsoft/referencesource/blob/master/System/net/System/URI.cs) NOTE: Seen in the Compress(char[] dest, ushort start, ref int destLength, UriParser syntax) method.

(https://github.com/microsoft/referencesource/blob/master/System/net/System/_UriSyntax.cs) NOTE: Compress() does the conversion: if ch=='\\' && ConvertPathSlashes then dest[i]='/'.

- [high] When building the escaped path, UriHelper.EscapeString is called with rsvd='%', and for every '%' followed by two valid hex digits it copies the three characters unchanged ('leave it escaped'), so valid %XX triplets such as %24, %20 and %2F, including their hex letter case, are not escaped a second time. (https://github.com/microsoft/referencesource/blob/master/System/net/System/UriHelper.cs) NOTE: Called from Uri.GetCanonicalPath with (input,..., true, '?', '#', '%').

**Recommendations:**
- Build the URL yourself with a SigV4-style encoder (uppercase hex, never encode unreserved, keep '/' in keys) and then sign new Uri(url).PathAndQuery, not your own string. Before sending, assert that it equals the signed canonical path and fail fast with a clear error if it does not.
- At startup, probe the Uri quirks at runtime: new Uri("https://h/a%2Fb/c./d").PathAndQuery should equal "/a%2Fb/c./d" in V3 mode. Record the result so the NAV admin sees whether the host runs in legacy mode.
- Reject or refuse object keys and blob names that contain '.' or '..' path segments, and always encode '\' as %5C. Neither HttpClient nor HttpWebRequest on .NET Framework can send these unchanged, and a dontEscape or UriSyntax workaround does not stop path compression.
- Do not use StringContent for signed bodies. Use ByteArrayContent or StreamContent and set Headers.ContentType to a parameterless media type, or sign exactly content.Headers.ContentType.ToString() so the '; ' re-serialization matches.
- For large uploads, use a seekable FileStream in StreamContent, or set content.Headers.ContentLength explicitly, and leave TransferEncodingChunked unset. Otherwise HttpClientHandler buffers the whole body in memory (up to Int32.MaxValue). Use S3 multipart or Azure Put Block for very large files.
- Never add Expect, Transfer-Encoding or Connection to SignedHeaders or the canonicalized headers. Optionally set request.Headers.ExpectContinue = false explicitly, keeping in mind that this changes the shared ServicePoint.
- Always pass an absolute Uri to HttpRequestMessage and do not use HttpClient.BaseAddress for signed requests, to avoid relative-reference resolution.
- Falling back to raw HttpWebRequest gains nothing for path fidelity, because it uses the same Uri.PathAndQuery. Only a raw socket or SslStream writer would bypass System.Uri, so choose key validation over a transport rewrite.
